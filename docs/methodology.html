Today Performance Methodology

What this is

A hobby model that projects strikeout totals for every MLB starting pitcher, compares them to sportsbook over/under lines, and ranks any positive-expected-value edges. It runs itself on a nightly cycle: every evening, once most games are done or well into their final innings, it scores the completed slate and projects the following day, and every morning it pulls the day's betting lines. Every projection is logged before games start and results are reconciled automatically. Nothing is ever deleted or cherry-picked — the Performance page is the whole record.

The update cycle

  • 7:00 PM AZ — nightly model refresh. Ingests the day's box scores so far, scores every logged projection, settles picks, and projects the following day's probable starters. This is when the board flips to tomorrow — and it flips because the code says 7 PM, not because of when the job happens to start. Because this now runs earlier than before, more games are typically still in progress at flip time (see "Honest limitations" below).
  • 8:00 AM AZ — morning odds run. Pulls game totals/moneylines and K prop lines for the day's slate from US books (free-tier credit budget), settles any games that finished after the nightly run, and rescores edges against the fresh lines.
  • 3:00 PM AZ — pre-slate refresh. Firmed-up lineups, plus a targeted re-pull of K props on the top-edge games to catch line movement.
  • Why those times are (roughly) exact. GitHub's own scheduler is best-effort and can run these jobs late by hours if left to a single daily check-in per slot. Rather than one check-in per slot, the workflow checks in every 15 minutes across each target window, so a late scheduler run still gets caught and published quickly — a check that finds the data already fresh exits in seconds, so this costs nothing extra. (An external on-the-minute scheduler can also fire these directly; see the repo's README for details.) The header on every page shows the last update and the next one, and flags a slot that is running late instead of quietly showing stale numbers.
  • Sunday overnight — weekly retrain on every start since 2022.
  • Manual: lines typed into lines/manual_lines.csv rescore within a couple of minutes; a "Run workflow" tap in the GitHub app forces a full refresh any time (an afternoon manual run also re-pulls props for the top-edge games to capture line movement).

Only FanDuel and DraftKings

The Today board only ever shows a line or a pick from FanDuel or DraftKings — the two books actually used day to day. Every other book The Odds API returns is still ingested and stored (it feeds the model and the full historical record below), it just never surfaces on the board. The Performance page goes one step further for its own bookkeeping: the same bet is usually offered at several books at slightly different prices, and for lifetime record-keeping that's one pick, not six — so Performance scores against a single canonical book per pick across the full set it stores (DraftKings when it has a line, otherwise the next book down a fixed chain), independent of which two books the Today board displays.

The model

A LightGBM gradient-boosted tree model with a Poisson objective produces the point estimate, and five separate quantile models (p10/p25/p50/p75/p90) trace the predictive distribution. A smooth monotone curve (PCHIP) through those quantiles gives the probability of clearing any line. It retrains weekly on an expanding window of every regular-season start since 2022 (postseason starts are handled separately — see below).

Features that feed the model, in order of importance

  • Pitcher swing-and-miss form: CSW% (called strikes + whiffs per pitch), SwStr%, and K% as exponentially-weighted averages with a half-life of ~5 starts. CSW% stabilizes much faster than K%, which is why it leads.
  • Opponent lineup K% vs handedness: slot-weighted strikeout rate of the nine projected hitters against the pitcher's hand, blending the last 30 days (60%) with the season (40%).
  • Expected workload: the pitcher's own recent batters-faced average, a team-level "quick hook" prior (that team's own starters' recency-weighted BF over their last 20 starts — computed in-house from logged relief appearances, no external dependency), and the game's run environment (Vegas total when available, otherwise both teams' recent scoring). The team prior exists because a manager's hook tendency is a property of the team/staff, not just that one pitcher's track record — a rookie's first few starts have no personal BF history to lean on, but his team's bullpen-usage pattern already does.
  • Stabilizers and context: K-BB%, fastball velocity trend (fatigue flag), park K factor, home-plate umpire tendency, temperature/wind for outdoor parks, home/away, days of rest.
  • Early-season prior: a Marcel-style regressed prior from last season, blended by sample size — the model leans on the prior in April and on current form by June (weight = BF / (BF + 70)).
  • Deliberately excluded: batter-vs-pitcher history (mostly noise under ~25 PA). Times-through-the-order (see "What isn't modeled yet" below) is also not an explicit feature, though the recency-weighted features above partially absorb it.

When lineups aren't posted yet

Lineup cards usually post 30–90 minutes before first pitch. Until then the model falls back: confirmed lineup → most-used hitters over the last 7 days → team-average K% vs hand. Each tier carries a lineup confidence (1.0 / 0.6 / 0.3) shown on every card, and lower confidence widens the projected range and discounts the edge score rather than pretending certainty.

Retraining without breaking live projections

The model retrains weekly but projects daily, so most days run against a model trained several days earlier. Whenever a feature is added or removed, each trained model records its own exact input list at training time, and projection always builds its feature vector from that specific model's list rather than the current code's list. That decoupling means adding a new feature can never crash or silently corrupt a projection running against the still-active older model in the days before the next retrain catches up.

Postseason mode

The board only started projecting postseason games starting the 2026 playoffs — earlier versions filtered the schedule to regular-season games only, so the board would have gone dark for all of October. Postseason starts are now shown, but handled deliberately differently from the regular season:

  • Not trained on postseason data. There isn't remotely enough postseason history yet (one or two Octobers' worth of starts) to train a reliable postseason-specific model, and mixing a handful of postseason rows into the regular-season training set would bias it rather than improve it. Training still filters to regular-season starts only.
  • A measured, inference-time-only adjustment instead. Postseason starters throw meaningfully fewer innings than in the regular season — FanGraphs' 2025 data puts it at ≈4.35 IP vs ≈5.19 IP, roughly a 16% reduction — but their per-inning quality doesn't decline (FIP is flat at ≈3.64 either way). That's a pure quantity effect: fully-rested, high-leverage bullpens let managers pull starters earlier, not that the starter's stuff gets worse. So rather than adjusting any K-rate or quality input, the model's full predicted distribution (point estimate and every quantile) is scaled down by that measured ratio (4.35/5.19) at prediction time only, for any Wild Card / Division / Championship / World Series game — training is completely untouched.
  • Revisited once there's real data. Postseason game type is tagged on every prediction, so postseason calibration can be tracked separately from the regular-season model's numbers — a handful of October starts should never quietly drag down (or flatter) the metric this site uses to judge the regular-season model. Once enough postseason starts accumulate across multiple Octobers, this stopgap gets replaced with an actually-trained adjustment.

Short-leash / workload flag

Some starts have a manager-imposed batters-faced ceiling decided before first pitch — a rookie on innings limits, a pitcher easing back from injury, a planned bullpen game. This is a different phenomenon from ordinary in-game fatigue: it's not about how a pitcher's stuff holds up as a lineup sees him more times, it's a pre-set cap on opportunities, and it's sometimes knowable in advance from beat-reporter coverage. The evidence for treating it this way — rather than as a stuff/quality adjustment — comes from the industry precedent of modeling two separate batters-faced "leash profiles" (normal vs. short) and widening the distribution when the outcome is uncertain, plus the finding that the general times-through-the-order penalty is driven by batter familiarity, not pitcher fatigue, so a manager pulling a starter early is capping opportunities, not protecting declining stuff.

In practice, real examples of this (a team's public language before a short-leash start) are almost never a clean number — it's soft, qualitative language days out ("we have to build him back up... in a mindful way"), not a same-day pitch-count press release. So this ships as a flag, never a hard number and never a silent model input:

  • A best-effort scrape (public X mirrors, same fragile-by-nature approach as everything else that touches X/Twitter, plus a phone-editable manual CSV fallback for when scraping is down or a handle isn't tracked yet) looks for a fixed set of phrases — "short leash," "pitch limit," "innings limit," "bullpen game," "built back up," and similar — in pregame coverage.
  • This is deliberately a conservative keyword/phrase match, not an AI model call. The evidence says an LLM would catch more of the soft, qualitative phrasing a numeric pattern misses — but that costs money per call, and this project runs under a strict zero-dollar rule, so wiring a paid API call into an unattended daily job isn't a decision to make silently. The keyword version is the honest free version: it will miss novel phrasing, but it will never invent a flag from nothing.
  • Trust but verify: every flag is cross-checked against that start's K line movement. If the line has already moved down since the flag showed up, it's marked corroborated (shown as a solid badge on the Today board); if not, it's marked unconfirmed (shown dimmer) rather than discarded — a single scraped tweet isn't a source to fully trust on its own, but it's still worth seeing.
  • It never touches the model or the projected number directly — it's a note under the pitcher's name on the Today board so it can be eyeballed before betting, nothing more.

What isn't modeled yet: times-through-the-order

Separate from short leash above: research on the times-through-the-order penalty (the general in-game decline as a starter faces a lineup multiple times) finds it's driven by batter familiarity, not pitcher fatigue — wOBA rises gradually across the first three trips through the order and then plateaus, and it's a continuous effect rather than a threshold you cross. It's partially absorbed here already through the recency-weighted form and workload features above, but there's no explicit "third-time-through" signal yet. Given the effect is continuous, a hard rule (cut K rate by X% past the second time through) would be the wrong shape for it — a smooth interaction feature would fit better if this gets added, but it's a lower priority than short leash was.

Edge math & pick ranking

For each K line we strip the vig from the two-way price (multiplicative method) to get the market's true win probability, and read the model's win probability off the projected distribution. The difference is the probability edge:

prob edge = model win % − vig-free market win %

Picks are ranked by probability edge, biggest first — it directly answers "how much more often does the model think this bet wins than the market does?" Each pick also shows the model's win %, expected value per unit, and a quarter-Kelly stake for sizing. Only positive-EV sides are surfaced — a high win probability at a price that still loses money long-run (heavy vig) is not a pick.

Signals tab — turned off (but the underlying system isn't)

There used to be a Signals tab: a pre-game validation view with GO/CAUTION/WAIT pick windows, a model/line/FanGraphs comparison, and capper picks scraped best-effort from X. It wasn't getting used and mostly repeated what the Today board already showed, and the capper scraping had stopped working reliably (X blocks free automated access), so the hourly job that fed that view is paused and the tab is off the nav. The code and data (kproj/signals/, docs/data/validation.json) are still in the repo if it's ever worth reviving — python -m kproj signals still runs it by hand.

The short-leash/workload flag above is built on that same isolated subsystem (same best-effort scraping shape, same rule that it can never touch the main database) but is a separate, currently-active feature — it runs on the same hourly cycle and its output surfaces directly on the Today board, unlike the retired Signals view.

How to read the Performance tab

Performance is the after-the-fact record. Everything on it follows the one-pick-one-book rule, and the page is built around one question: what did the model say vs. the book line, and how did it hold up?

  • Model vs. the book lines: the headline section. On every canonical line the model was graded against — not just the ones it liked enough to recommend — take whichever side it favored: what's the record and net units, and who called the Ks closer, the model or the book (MAE, with a monthly breakdown)? The ledger table underneath is the full pick-by-pick history, newest first; the green dot marks the subset that was also a positive-EV recommendation.
  • Positive-EV betting record: the narrower, real-money question — of the picks that were actually a recommended bet, what's the ROI, hit rate, and net units at 1u flat? The low-sample warning stays up until ~500 settled picks.
  • Model quality: MAE and bias of the raw K projections plus p10–p90 coverage (target ≈ 80%) — accuracy independent of any betting.
  • Calibration: predicted win % vs what actually happened, in buckets. Dots on the diagonal mean the probabilities can be taken at face value.
  • Model versions: each trained model's backtest vs. live error.

Closing-line value (CLV) isn't tracked on this page — it only ever gets measured when a closing line happens to be entered manually, which was too sparse and too easy to over-read, so it's gone rather than shown as an incomplete number.

Honest limitations

  • K prop lines pull once each morning (free-tier credit budget), with a targeted re-pull on the top-edge games at 3:00 PM AZ. Lines can still drift after that.
  • The 7:00 PM AZ refresh is an hour earlier than it used to be, so more games — not just East-coast night games and late West-coast starts, but some still-in-progress games generally — are unsettled at flip time and finish reconciling on the next morning's run. That is why a just-flipped evening board shows yesterday's results as partial, more often than before.
  • The postseason BF adjustment is a measured stopgap, not a trained model — there isn't enough postseason data yet to train one properly (see "Postseason mode" above).
  • The short-leash flag is best-effort and conservative by design: it can miss real short-leash situations phrased in ways its keyword list doesn't cover, and it depends on public X mirrors that are frequently unreliable.
  • Retractable-roof parks: day-of roof status isn't freely available, so weather is attenuated rather than exact.
  • Trust the calibration plot and 30-day panel over any single hot streak; below ~500 settled picks the ROI number is mostly luck either way.
